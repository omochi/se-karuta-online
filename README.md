# Swift Evolution Karuta Online

Swift Evolution の4択カルタを、進行役・会場ディスプレイ・参加者のスマートフォンで遊ぶ Web アプリ。略称は **SE Karuta**。

運営への共有には、実画面と構成図を使った[説明つきスライド](#このゲームの提案資料)を用意しています。遊び方と当日の進行を16枚にまとめ、本体のトップページ下部から開けます。

React + Cloudflare Workers / Durable Objects / D1。ローカルで大会作成から出題・回答・最終表彰まで一通り試遊できます。4種類の表彰・大会最速回答、問題ビューワでの編集・JSON保存、Displayプレビューも実装済みです。Cloudflare の本番リソースは作成・変更していません。

## ローカル起動

Node.js 22.22 以上を用意し、プロジェクトのルートで実行します。

```sh
npm ci
npm run setup
npm run dev
```

`setup` は `.dev.vars` がなければ作成し、ローカル D1 にマイグレーションを適用します。既存設定や大会は削除しません。管理用パスワードの初期値は `local-karuta`、セッション署名鍵はランダムに生成します。

[http://localhost:5218](http://localhost:5218) を開きます。ポート **5218** は、サンプル問題の **SE-0218 (compactMapValues)** にちなんでいます。使用中なら別ポートへ自動で変更せずエラーにします。

別のターミナルで、本編8問（入門3問・標準3問・難問2問）を登録できます。

```sh
npm run seed
```

作成した大会の Control / Display / Player の URL が表示されます。試遊大会の Display 用パスワードは `display-karuta`。コマンドを再実行すると別の大会を作成します。管理画面から独自の問題 JSON を登録することもできます。

## Cloudflare の認証とデプロイ先アカウント

手動デプロイの認証は Wrangler のブラウザーログインを使います。

```sh
npx wrangler login
npx wrangler whoami
```

本番用の設定は、初回にローカル用の設定をコピーして用意します。既存の `wrangler.production.jsonc` がある場合は上書きせず、そのファイルを編集してください。

```sh
cp wrangler.jsonc wrangler.production.jsonc
```

コピー先で、次の項目を本番用に設定します。

- トップレベルに `account_id` を追加し、`whoami` に表示されるデプロイ先の Account ID を指定します。
- `name` を本番 Worker 名（例：`se-karuta-online`）に変更し、`workers_dev` を `true` にします。
- `vars.PUBLIC_ORIGIN` を追加し、`https://<Worker名>.<アカウントのサブドメイン>.workers.dev` を指定します。
- `d1_databases` の `database_name` と `database_id` を、作成した本番 D1 の名前と ID に変更します。`binding` は `DB` のままにします。

`wrangler.production.jsonc` は Git 管理外です。Account ID・DB ID・公開URLを本番設定にまとめ、ローカル開発用の `wrangler.jsonc` には個人の Account ID を書きません。以前 `.env` に設定した `CLOUDFLARE_ACCOUNT_ID` は削除できます。ログイントークンは Wrangler が管理します。アプリのローカル設定（`PUBLIC_ORIGIN` など）は、引き続き `.dev.vars` に設定します。

本番の D1 操作やシークレット登録では、`--config wrangler.production.jsonc` を指定します。初回デプロイには本番 D1 の作成と、`ADMIN_PASSWORD` の本番シークレット登録が必要です。マイグレーションは下記のデプロイコマンドで適用します。

次のコマンドで、本番設定を指定したビルド → 本番D1の未適用マイグレーションの自動適用 → Vite が生成した設定でのデプロイを順に実行します。未適用のマイグレーションがなければそのまま進み、ビルドやマイグレーションに失敗した場合はデプロイしません。

```sh
npm run deploy
```

公開せずにビルドとデプロイ設定を確認する場合は、`npm run deploy -- --dry-run` を使います。この場合、マイグレーションの適用はスキップし、本番DBは変更しません。本番設定の指定はビルド時だけ有効で、通常の `npm run dev` には影響しません。

出力先の `se_karuta_online` は Worker 名のハイフンをアンダースコアに置き換えた名前です。`name` を変更した場合は、`scripts/deploy.mjs` の `outputConfig` も合わせてください。

## 大会一覧

管理者ログイン後のトップページには、作成日時が新しい大会を最大5件表示します。「すべての大会を見る」から `/events` を開くと、20件ずつ前後のページへ移動できます。各大会には「準備中・進行中・終了」を表示し、過去の大会と成績も引き続き確認できます。大会一覧は管理者専用です。

## このゲームの提案資料

トップページ下部の「このゲームの提案資料」から `/proposal/` を開けます。ローカルでは `npm run dev` の起動後、[http://localhost:5218/proposal/](http://localhost:5218/proposal/) でも確認できます。ログインは不要です。

- 16枚のスライドと説明文を収録し、「発表モード」でスライドだけ、「一覧で読む」で説明文と一緒に表示できます。
- 通常表示は左にスライド、右に説明文を配置し、長い説明文だけペイン内でスクロールできます。スマートフォンの縦画面では上下に配置します。
- 左右キー、Page Up / Page Down、画面上のボタンで移動できます。`/proposal/#3` のように各スライドへ直接リンクできます。
- スクリーンショットを押すと拡大します。画面と成績はローカルのデモデータです。
- 問題が写る画面は、公開用の [`data/questions/tutorial.json`](data/questions/tutorial.json) の1問だけで撮影しています。画像を更新するときもこの問題を使い、本番用の問題・選択肢・正解が資料に出ないようにします。

実体は [`public/proposal/`](public/proposal/) の静的なHTML / CSS / JavaScriptです。Viteがそのままビルド出力へコピーし、本体と同じWorkersのStatic Assetsで配信します。Reactのルートには組み込まず、通常のリンクで移動します。GitHub Pages用の公開ワークフローはありません。

内容を更新する場合は、`public/proposal/slides.json` の文言・説明文・図の配置、`public/proposal/assets/` のスクリーンショットを編集します。ページ送りやレイアウトは `slides.js` と `style.css` にあります。HTMLファイルの直接オープンではなく、HTTP経由で確認してください。

## スマートフォンで試す・公開URLを設定する

`.dev.vars` の `PUBLIC_ORIGIN` に、**スキーム・ホスト・ポートを含む公開元URL**を指定します。パスは付けません。

```dotenv
PUBLIC_ORIGIN=http://192.168.1.2:5218
```

変更後、サーバーを再起動します。

```sh
npm run dev
```

同じネットワークのスマートフォンで [http://192.168.1.2:5218](http://192.168.1.2:5218) を開くか、Control / Display の QR コードを読み取ります。IP アドレスは使用するマシンに合わせて変更してください。

- 参加用 QR コード・画面リンクはサーバーが `PUBLIC_ORIGIN` から生成します。リクエストの `Host` / `X-Forwarded-Host` から推測しません。
- 別のホスト名から開いた画面は、設定された公開URLへ移動します。WebSocket の接続先と操作の Origin 検証も同じ設定を使います。
- ホスト名を変更するとブラウザーの Cookie が別扱いになるため、進行役・Display は再ログイン、参加者は再登録になります。大会を始める前に URL を固定してください。
- `dev` はローカル開発サーバーを LAN に公開します。会場の Wi-Fi が端末間通信を制限している場合は接続できません。
- `seed` の通信先は既定でループバックです。表示するURLと Origin ヘッダーには設定値を使います。ポート自体を変えるときは `vite.config.ts` と `PUBLIC_ORIGIN` を揃え、`LOCAL_URL=http://localhost:新ポート npm run seed` とします。

本番では Workers の環境変数に `PUBLIC_ORIGIN=https://公開ホスト名` を設定する設計です。実際の本番構築・ドメイン設定・秘密値の登録は未実施です。

## 参加コードで入る

Control と待機中の Display に、大会固有の参加コード（例：`ABCDEF`）とトップページのURLを表示します。参加者はそのURLを開き、コードを入力してから名前を登録します。QRコードも引き続き使えます。

- 英字6文字。読み違えやすい I・L・O は使いません。小文字・空白・全角での入力も受け付けます。
- コードは大会作成時に発行し、進行中・再起動後も変わりません。終了した大会への新規参加はできませんが、有効な共通セッションとその大会の参加情報がある人は、コードからも結果画面へ戻れます。
- 管理・表示用パスワードとは別の公開識別子です。コードだけで管理画面には入れません。
- 認証にはドメイン共通の `se_session` Cookieを一つ使います。Cookieにはランダムなトークンだけを置き、サーバー側で匿名クライアントIDと大会別の参加者・Display権限、管理者権限を管理します。同じブラウザーでA大会とB大会に別名で参加でき、管理者・Displayとしてログインしても参加者の紐づけを維持します。
- 同じ大会では以前の参加者ID・名前で自動復帰します。共通セッションを持つクライアントの同時参加は、一つの参加者へ収束します。Cookieがまだない初回リクエストを同時送信した場合は、別クライアントになることがあります。
- セッションは発行から30日で失効し、自動復帰や再ログインでは延長しません。Cookie消失・期限切れでは新しいクライアントとして登録し、同名だけで過去の成績を引き継ぎません。旧参加者は名簿に残るため、必要に応じてControlで「開始を待たない」にしてください。
- 既存環境は `npm run db:migrate` を実行して開発サーバーを再起動してください。既存大会は初めて開いたときにコードを発行し、保存済みの問題・回答・結果を維持します。

### 認証データの移行と失効

`0004_client_sessions.sql` は匿名クライアント・セッション・大会別の参加者紐づけ・Display権限を追加し、参加者に保存していた旧セッションハッシュを取り除きます。既存の大会・参加者・回答・成績は保持します。過去の参加者には新クライアントを自動で紐づけません。旧 `se_player_*`・`se_display_*`・`se_admin` Cookieは受け付けず、参加登録または各ログインから新しい共通セッションを発行します。旧Cookieは元の期限で消えます。署名鍵 `SESSION_SECRET` は不要になりました（既存の設定に残っていても使いません）。

APIとWebSocketの接続時に、DBのセッション期限と要求された役割の権限を検証します。接続中も大会ごとに約15秒おきにまとめて検証し、期限切れ・セッション削除・権限の削除を検出した接続を閉じます。各メッセージでは接続時の期限も確認します。DB障害時は検証できない接続を閉じ、再接続で認証し直します。失効のための管理UI・APIはなく、DB上の `client_sessions` の削除、`clients.is_admin` の解除、`client_displays` / `client_players` の紐づけ削除が反映されます。回答ごとのDB認証は行いません。

## 遊び方

1. Control で次の問題・正解・解説を事前確認し、必要に応じて同じDisplay URLを会場の各モニターやサテライト用PCで開き、Display用パスワードで入室します。Displayは任意で、いつでも追加・切断できます。
2. 参加者は QR コードを読むか、トップページで参加コードを入力し、名前を登録します。
3. 「最初の問題を開始」を押します。選択肢は伏せ、「全員の接続を待っています」と準備完了人数 / 対象人数を表示します。
4. Controlでは参加者ごとに「開始を待つ／開始を待たない」を切り替えられます。待つ設定の参加者全員の準備が揃ったら、公開前5秒 → 選択肢公開・出題まで20秒 → 問題公開・回答受付（難易度1・2・3の初期値は30・45・60秒） → 自動締切と進みます。各カウントダウンには残り秒数と横長バーを表示します。
5. 未回答者がもう少し考えたいときは、Control の「＋15秒」で現在の回答期限を15秒ずつ延長できます。全画面のタイマーに「15秒延長！」を5秒間表示します。次問の時間設定と回答済みの回答・回答時間は変えません。期限を過ぎた後や手動締切後の延長はできません。
6. 締切で未回答者は「回答なし」になります。Control で正解・先着順位を順に公開して次の問題へ進みます。正解発表から順位公開まで、DisplayにはA〜Dの回答人数を横棒グラフで表示し、正解の強調と未回答人数を添えます。早期の手動締切もできます。
7. 終了すると正答王・早押し王・安定王・難問王の結果を表示します。難問王は、締切時に正解が最多得票ではなかった問題の正解数です（同率最多は対象外）。

問題文は共有 Display に表示し、参加者は4つの選択肢から回答します。回答は1問1回で変更できません。通信切断時は自動再接続し、回答を再送しても最初に保存した回答を維持します。開始を待つかどうかの設定は切り替えるまで維持します。待たない人も締切まで回答でき、回答しなければ通常の未回答です。待つ設定への復帰は次問から反映し、途中参加者も次問から回答対象になります。問題を無効化すると全表彰の集計から除外します。

公開前・選択肢公開中の時間と、難易度1・2・3ごとの回答時間を大会ごとに保存します。Control の右ペイン最下部にある「時間の設定」で各1〜600秒の整数に変更でき、進行中の期限は維持して次に始まる段階から反映します。旧形式で保存済みの共通回答時間は全難易度へ引き継ぎ、時間設定のない既存大会には新規大会と同じ初期値を使います。次問では前問の選択状態もクリアします。

参加者の準備完了通知は待機画面の DOM 反映・描画機会・タブの可視状態に基づきます。選択肢は公開前カウントダウン終了後に配信します。人間が実際に読んだことや端末間の完全な同時表示を保証するものではありません。Displayは準備確認の対象にせず、0台でも開始できます。表示は運営が目で確認します。Controlには接続台数と各画面の接続状態を表示します。追加・切断・再接続は進行に影響せず、新しい画面にも現在の問題と同じ期限を配信します。

開発中に `src/worker/` のコードを変更した場合は、開発サーバーを再起動してください。ホットリロードで既存 WebSocket とタイマーの状態がずれる場合があります。通常の大会進行ではページのリロードは不要です。

保存済み大会で従来「お休み」として回答対象外だった記録は、`0003_unify_resting_with_unanswered.sql` で回答対象へ変更します。回答がなければ未回答として正答率の分母に含め、結果・レポートを再集計します。参加者や回答そのものは削除しません。

## 終了した大会の詳細結果（管理者専用）

終了した大会のControlから「詳細結果を見る」で `/e/:id/control/report` を開きます。管理用パスワードで認証し、参加者・Displayからは取得できません。

- **全体の集計**：有効・無効・未出題の問題数、正答率、回答数、平均回答時間、最終表彰。
- **問題ごとの内訳**：正答率順の並べ替え、A〜Dの回答分布、平均・中央・最速正解時間、問題文・解説、全参加者の回答。
- **参加者ごとの成績**：名前・識別子での検索、正解数・正答率・正解時の平均時間などでの並べ替え、表彰に関わる成績、全問の回答履歴。問題と参加者の詳細を相互に開けます。

全体・個人成績は有効問題だけを集計します。正答率の分母には未回答を含め、途中参加前の対象外を除きます。無効問題は理由と回答記録を残し、受付開始前に無効にした場合は「受付前」と表示します。未出題や対象データなしは0秒・0%と混同せず表示します。平均・中央値は回答済みのデータだけで計算します。

データは終了後の保存済み大会から読み取ります。

### ダミー大会ですぐ確認する

ローカルDBに終了済みのサンプル大会を追加できます。事前に `npm run setup` でDBを準備してください。開発サーバーが起動していなくても追加できます。

```sh
npm run seed:report
```

大会名は「【ダミー】詳細結果サンプル大会」。16人・12問（有効8問・無効2問・未出題2問）で、正解・不正解・未回答・途中参加・同名参加者・同着・受付前後の無効化を含みます。大会一覧からControlを開くか、コマンドが表示する詳細結果URLへアクセスできます。Display用パスワードは `display-karuta` です。

実行ごとに新しい大会を追加します。既存大会や問題原本は変更せず、Cloudflare本番には接続しません。

## 問題データ

作問・解説リンク・レビューのルールは[作問マニュアル](docs/question-authoring.md)にまとめています。解説のリンク先には koher さんの Swift Digest の日本語要約を使います。

[`data/questions/vol-01.json`](data/questions/vol-01.json) を参考にします。`id`、`difficulty`（1: 入門、2: 標準、3: 難問）、`bodyMarkdown`、A〜D の `choices`、`correctChoice`、`explanationMarkdown` を持つ配列です。CLI は `questions` プロパティで包んだ形式も読み込みます。問題数は1〜100問、各文字数・ID重複・選択肢数・難易度を検証します。第1集の本編は入門3問・標準3問・難問2問の計8問です。時間がある場合の追加出題用に、[`data/questions/vol-01-bonus.json`](data/questions/vol-01-bonus.json) へ入門1問・標準1問・難問2問の計4問を難易度順で収録しています。ボーナスは別の問題集として問題ビューワで確認したり、大会作成時に読み込んだりできます。旧JSONで難易度がない場合は2として読み込みます。

選択肢の `choices.A`〜`choices.D` は、SE番号・原題・邦題・解説URLをまとめたオブジェクトです。4つのプロパティは必須で、邦題が原題と同じ表記の場合は `titleJa: null` で邦題なしを明記します。`explanationUrl` には、対応する Swift Digest 記事の HTTPS の絶対URLを保存します。

```json
"choices": {
  "A": {
    "number": "SE-0380",
    "title": "if and switch expressions",
    "titleJa": "ifとswitch式",
    "explanationUrl": "https://swiftdigest.koherent.org/proposals/se-0380.html"
  },
  "B": {
    "number": "SE-0289",
    "title": "Result builders",
    "titleJa": null,
    "explanationUrl": "https://swiftdigest.koherent.org/proposals/se-0289.html"
  }
}
```

上は2択分の抜粋です。実際の問題にはA〜Dの4択を定義します。邦題は [Swift Digest](https://swiftdigest.koherent.org/proposals/) から事前に取得してJSONへ保存し、実行時には外部取得しません。第1集とチュートリアルには2026-10-26時点の邦題を収録しています。文字列形式の選択肢は読み込めません。更新したJSONから新しい大会を作成すると反映されます。

Display の正解発表画面では、全選択肢の右端に解説リンクのアイコンを表示し、別タブで Swift Digest を開きます。URL は SE番号や解説本文から組み立てず、JSONの値をそのまま使います。`explanationUrl` のない旧JSONは読み込めません。問題ビューワで各選択肢のURLを編集してJSONへ保存できます。

```sh
npm run questions:check
npm run questions:check -- path/to/questions.json
```

問題・正解をクライアントの静的ファイルへ含めず、役割と進行段階に応じたデータだけを WebSocket で送ります。大会作成時に JSON を取り込みます。本番で使う問題セットは別途レビューしてください。

## 問題ビューワ

トップ画面または Control の「問題ビューワ」から `/questions` を開きます。管理用パスワードは大会管理と共通です。

1. 大会を選んで「大会から読み込む」、または問題 JSON をファイル選択・貼り付けで開きます。
2. 一覧・検索・前後ボタンで問題文・選択肢・正解・解説を確認します。正解の表示、暗い背景を切り替えられます。
3. 「この問題を調整する」を開いて本文・選択肢・難易度などを編集すると、すぐにプレビューへ反映されます。
4. 「JSONをダウンロード」で保存し、次の大会作成時に取り込みます。

「Displayプレビューを開く」で、本番Displayと同じレイアウトを別タブに表示できます。普通のリンクなので、ブラウザーの操作で別ウィンドウにも開けます。問題の選択・編集は自動で反映され、「出題中」（初期状態）・「選択肢公開」・「正解発表」を切り替えられます。タイマーは選択肢公開20秒・出題中は難易度1・2・3に応じて30・45・60秒の初期値で固定し、ウィンドウを会場の画面サイズに合わせて、コードや選択肢の収まりを確認できます。正解発表では「サンプル」と明記した回答分布も表示します。大会への接続や登録は行いません。ビューワを閉じる・別ページへ移動すると、プレビューは案内表示に戻ります。

Displayでは問題開始後の接続待ち・選択肢公開前のカウントダウンから、選択肢公開中も「難易度 1 ★☆☆」のように数字と星のバッジを表示します。問題文の公開後は本文の前に表示します。難易度は表示と回答時間の選択に使い、得点・表彰の計算には影響しません。

出題中から締め切り後の正解発表待ち・正解発表まで、問題文を表示し続けます。ヘッダーと選択肢を小さくし、残った領域に本文・コード・注記が縦横とも収まる最大の文字サイズ（上限32px）を自動で選びます。コードは折り返しません。計測は描画前に完了させ、タイマー更新では再計測しません。ビューワにはプレビューの表示領域と本文サイズを表示し、18px未満なら問題の短縮を案内します。極端に長く最小サイズでも収まらない問題は、切り捨てずスクロール可能にし、収まらないことをビューワへ通知します。

編集内容は画面内にだけ保持します。元ファイルと既存大会は変わりません。ダウンロード前にページを閉じると編集を失うため、離脱時には確認を表示します。外部エディターで変更したファイルは、同じファイルを選び直して再確認できます。

## 実装と検証

- `src/client/`: 3画面・認証画面・QR・WebSocket 再接続。
- `src/worker/`: API、認証、大会ごとの Durable Object、ゲーム進行、D1 永続化。
- `src/shared/`: 公開データ型・問題検証・公開URL生成。
- `migrations/`: 正規化した大会・問題スナップショット・参加者・参加資格・回答。

Durable Object が大会内の操作を直列化し、D1 への保存成功後に受理通知と状態更新を送ります。DO が再起動したら D1 から復元します。初期版は通常の WebSocket 接続を使い、接続中の DO の休止は採用していません。タイマーには DO の alarm を使います。

```sh
npm run check
```

表示の自動調整は、開発サーバーの `/tests/fixtures/display-fit.html` でも確認できます。「描画フレームを検証」で、短文・日本語の折り返し・長いコード・問題の切り替えを最初の描画フレームから検査し、タイマー更新で再計測しないことも確認します。テスト専用の問題だけを使い、大会には接続しません。この検証ページは本番ビルドには含まれません。

出題前の難易度表示は `/tests/fixtures/display-difficulty.html?phase=countdown&difficulty=3` で確認できます。`phase` は `choicesPreparing`・`countdown`・`choicesReading`・`acceptingAnswers`、`difficulty` は1〜3を指定できます。公開チュートリアルを使い、実際のゲームロジックがDisplay向けに返すデータを描画します。

邦題のレイアウトは `/tests/fixtures/proposal-titles.html` で確認できます。第1集の全問を、運営・Display・回答の各モード、選択肢公開・回答受付・締切・正解発表・ランキングの各段階で表示できます。解像度はPC・Display／スマホ・タブレットのプリセットから選べます。モード・問題・進行・解像度は選択すると即座に反映され、現在の設定はURLにも保持されます。回答モードへの切り替え時は390×844、回答から他モードへ戻ると1280×720になります。幅・高さは iframe の表示領域に適用され、実際のメディアクエリーと本文の自動調整が動きます。大会の作成・接続は行いません。

回答画面は選択肢の上に56pxのお知らせ枠を常に確保し、送信中・受付済み・通信エラー・再接続の案内を同じ領域に表示します。選択前後で枠線の幅も変えず、4択の位置と折り返しを維持します。スマホには他の参加者の回答済み人数を表示せず、開始前の参加人数と接続待ちの準備完了人数だけを表示します。ブランド・大会名・本人名・接続状態は通常のページフッターにまとめ、スクロールに追従しません。正解発表後の順位や詳しい結果は選択肢の下に表示します。

開発プレビューの「全問の収まりを検証」は、スマホ2サイズ×本編全8問について、実際に回答を押して未選択・送信中・受付済みで4択・進行表示・お知らせ枠・フッターの位置が変わらないことも検証します。固定状態の確認には、URLへ `answer=B&answerState=pending`（送信中）、`answer=B&answerState=accepted`（受付済み）、`answerState=error`（通信エラー）、`answerState=offline`（再接続）を付けられます。

純粋なゲームロジック・認証・URL検証、ローカル workerd による D1 の保存失敗時のロールバックと DO 再生成、Miniflare で40参加者の WebSocket 接続・同時回答・再接続・結果集計を確認します。統合テストは独立した一時DBを使い、回答受付30秒を含む実タイマーを含みます。開発サーバーは不要です。

回答時間の延長は `/tests/fixtures/answer-extension.html` で確認できます。「残り5秒から確認」→「延長を試す」の順に押すと、390×844のスマホ表示で15秒延長の通知と選択肢の位置・サイズが変わらないことを検証します。`?mode=control`・`?mode=display` で運営・会場画面も確認できます。公開チュートリアルだけを使い、大会には接続・保存しません。

テーマは [Swift 公式SVG](https://www.swift.org/assets/images/swift.svg) の `#F05138` を基準とし、文字とボタンには読みやすい濃淡を使っています。Swift 公式のサービスではありません。

本番前には、問題内容と所要時間・表彰条件の確認、実機スマートフォン・会場回線でのリハーサル、本番Cloudflare環境の構築・デプロイ・負荷確認、保存期間と削除方針の決定が残っています。

現在の実装状況、本番前の確認事項、ストレッチゴールの状況は [`docs/spec.md`](docs/spec.md) に整理しています。

Displayの回答速報は `/tests/fixtures/display-live-votes.html` で確認できます。「集計と正解発表を検証」で、対象20人の1票が5%になること、回答追加から締切・正解発表までバーのDOM・位置・長さを維持すること、少数側の正解だけを強調することを検証します。公開チュートリアルと本番のゲーム処理を使い、大会には接続・保存しません。`?width=1024&height=768` のように表示領域を指定でき、`snapshot=acceptingAnswers`・`snapshot=answerRevealed` を追加すると同じ15票の状態で撮影できます。
