# 作問マニュアル

Swift Evolution Karuta Online の問題を作成・レビューするときの共通ルール。少数の試作に対するレビューを反映しながら、生成ルールとコツをこの文書に蓄積する。

## 題材と難易度

- Swift の設計や実用上の意味を知ると面白い、重要な Proposal を題材にする。
- 基本的な問題に加えて、関連する Proposal の役割の違いや、コードが成立する理由を考える歯応えのある問題も用意する。
- マニアックな細部を知っているだけで決まる難しさを狙わない。
- コードや問題文から、正解を選ぶ決め手が読み取れるようにする。

### 第1回試作のレビューで確認した方針

統合問題集 [`vol-01.json`](../data/questions/vol-01.json) の難易度2（旧 `draft-01.json`）の3問は、重要な言語機能を押さえ、機能とコードの関係の理解を求める点が高く評価された。**この3問を標準難度の基準とする**。今後もこの方向を基準にする。

この難易度でも十分に歯応えがあるため、回答受付の初期値を15秒から30秒に延ばす。コードを読んで考える時間を確保し、難しさを増やすこと自体を目標にしない。

### 第2回試作のレビューで確認した難問の方針

統合問題集 [`vol-01.json`](../data/questions/vol-01.json) の難易度3（旧 `draft-02.json`）の3問も、出題者から「めっちゃいい」と評価された。標準より一段深い理解を問う難問の参考例とし、次の方針を継続する。原文との整合性などの最終精査は別途行う。

- 隔離・エラー型・コピー可能性など、重要な機能がコードに与える保証や制約を読み取らせる。
- 関連する基礎機能の導入と、今回のコードを成立させる拡張を区別させる。
- 成立する例と成立しない例の差を使う。未知の細かい仕様や長いコードを増やして難しくしない。

## ファイル名と問題ID

- 問題集は `vol-01.json`、`vol-02.json` のように連番で管理する。表示名は「Swift Evolution Karuta 第1集」のように付ける。
- 問題IDは `compact-map-values` や `builder-opaque-branches` のように、題材を表す短い英語の kebab-case にする。
- `demo`・`draft` などの作成経緯、問題集の巻数、出題順、難易度をIDに含めない。並べ替えや別の問題集への収録、難易度の変更でもIDを維持する。
- 異なる問題には、問題集をまたいでも異なるIDを付ける。登録後のIDは原則として維持する。
- 問題IDは作問・管理用。参加者向けの配信では別途生成した大会内の出題IDを使うため、題材が読み取れる名前でよい。

## 難易度の指定

- 各問題の `difficulty` に1（入門）・2（標準）・3（難問）を明記する。現在の問題集は各難度4問ずつ、計12問。
- 難易度は問題文と一緒に数字・星のバッジとして表示する演出であり、回答時間・得点・難問王の集計条件とは別の設定。
- 旧JSONは省略時に2を補うが、新しく作る問題には必ず明記する。

## 出題順

- 難易度順に固めず、序盤は入門で慣れてもらい、その後は標準・難問の間に入門も挟む。難問が連続しないようにし、最後は歯応えのある問題で締める。
- 難易度の並びを毎回同じ周期にせず、題材の偏りも見ながら問題集ごとに調整する。JSONの配列順を出題順とする。

## 誤答の選択肢

- 誤答候補は各問題の題材に合わせて選ぶ。同じ固定の選択肢セットを全問で使い回さない。
- 同じ分野の機能や、似ているが役割の異なる Proposal を使い、問題文・コードの決め手で区別できるようにする。
- 入門の問題でもこの方針を適用する。機能名とコードの対応で答えられる分かりやすさを保ち、細かな仕様の暗記を要求しない。
- 解説には、正解の理由に加えて誤答候補との違いを短く示す。
- 紛らわしい候補の数や組み合わせを固定しない。「構文を導入した提案」「同じ目的を別の方法で達成する提案」「コードの一部分だけを説明できる提案」などを、その問題に自然な範囲で混ぜる。
- 「一番新しい提案」「基礎機能より後の拡張」を選ぶだけで正解できる傾向を避ける。導入時期ではなく、コードの一行や適用対象の違いが決め手になるようにする。
- 最初の9問は各問の誤答候補を1つずつ近い題材へ差し替えて調整した。この変更数を今後の作問の固定ルールにはしない。

## 解説のリンク先（確定ルール）

- `explanationMarkdown` に載せる Proposal の解説リンクは、**koher さんの [Swift Digest](https://swiftdigest.koherent.org/) の該当記事を使う**。日本語で要約を読めることを優先する。
- GitHub の Proposal 原文リンクを参加者向け解説の標準にしない。draft・本番用の問題とも同じルールを適用する。
- リンクの表示名は `Swift Digest：SE-XXXXの日本語要約` とし、対象の Proposal が分かるようにする。
- URL は `https://swiftdigest.koherent.org/proposals/se-XXXX.html`（番号は4桁）。リンク先を開き、番号と記事タイトルが合っていることを確認する。
- 問題・解説の厳密な根拠や原文との整合性は、出題者が後のレビューで精査する。生成時に原文の根拠リンクを解説へ付けることを必須にしない。
- 該当する Swift Digest の記事が見つからない場合は、リンクを推測で掲載せず、レビュー時の確認事項として伝える。

例：

```markdown
[Swift Digest：SE-0143の日本語要約](https://swiftdigest.koherent.org/proposals/se-0143.html)
```

## 試作とレビュー

1. 大量生成の前に、まず3問程度を試作する。基準となる問題は [`vol-01.json`](../data/questions/vol-01.json) に統合し、difficulty の1・2・3で入門・標準・難問を区別する。
2. 出題者が難易度・面白さ・説明の分かりやすさをレビューし、その意見をこの文書へ反映する。
3. 問題ビューワの Display プレビューで、実際の表示領域にコードと選択肢が収まるか確認する。文字が小さすぎる場合は問題文・コードの分量を調整する。
4. `npm run questions:check -- data/questions/vol-01.json` などで対象ファイルの形式を検証する。

試作はレビュー前の状態として扱い、本番用に確定する前に出題者が内容を精査する。
