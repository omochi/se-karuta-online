# Swift Evolution Karuta Online — Product / Development Handoff

Swift Evolution のイベント向けクイズゲームを作る。

正式なプロダクト名は「Swift Evolution Karuta Online」とする。画面上のロゴや短い呼び名には、略称「SE Karuta」を使う。

既存の「Swift Evolution カルタ」は、テーブル上に Proposal の断片を書いた札を並べ、進行役が Proposal title を読み上げ、参加者が対応する札を取るゲームだった。

しかし参加者が習熟した結果、第二回では近くにある札が 0.3 秒程度で取られるようになり、知識より席順・反射速度の影響が大きくなった。

そこで、元のカルタらしい「知識 + 早さ」は残しながら、全員が同時に参加できるデジタル版を作る。

この文書は現在の実装に対応する仕様をまとめる。本番前の確認事項と、ストレッチゴールの状況は「本番前の確認・調整事項」「ストレッチゴールの状況」に分けて記載する。

## 現在の到達点

ローカル環境で、大会作成・参加から出題、回答、最終表彰まで一通り遊べる状態。4種類の表彰・大会最速回答に加え、準備用の問題ビューワ、編集・JSON保存、本番と同じレイアウトのDisplayプレビューも実装済み。

終了した大会はControlから管理者専用の詳細結果画面を開き、問題・参加者ごとの回答や集計を確認できる。`npm run seed:report` でローカルDBに終了済みダミー大会を追加して試せる。

問題集は `data/questions/vol-01.json` に入門・標準・難問を4問ずつ、計12問を収録している。作問・レビューのルールは[作問マニュアル](question-authoring.md)を参照する。

Cloudflare本番へのデプロイと負荷確認、実機スマートフォン・会場回線でのリハーサルは未実施。ローカルの自動テストと本番環境での確認は区別する。

## 最重要方針

- 一発もののイベントなので、システムは可能な限りシンプルにする。
- 想定参加者数は 10〜40 人。初期版は 1 会場での 1 大会の進行を中心に設計する。
- 当日の障害要因を減らし、通信切断や退室があっても進行役が対処できるようにする。
- 当日のシステムに AI / LLM を組み込まない。問題は事前に生成・人間がレビューして登録する。
- 当日は問題配信、回答、集計、ランキングを担当する。
- 参加者ごとの回答速度を計測するが、原理的な通信遅延や多少の不公平は許容する。
- 「最速の 1 人しか楽しめない」ゲームにしない。
- WebSocket で全画面を自動更新し、通常の進行にリロードを必要としない。
- Cloudflare Workers + D1 + Durable Objects を採用する。

### ページ間の遷移

- React Router の Data Mode を使う。同じタブ内のリンクは `Link`、大会作成後は `navigate` で移動する。
- 設定・大会一覧・認証・URLで指定された問題集は loader で取得する。大会画面は WebSocket の初回状態の受信も待ち、接続をそのまま画面へ引き継ぐ。
- loader の完了までは現在の画面を維持し、取得後に遷移先を表示する。「接続しています」「大会を読み込んでいます」といった中間画面は挟まない。初回アクセス時は背景色だけを表示し、ロゴや文言は出さない。
- 遷移キャンセル時には未完了のHTTP取得・先読み接続を破棄する。表示中の大会の接続は次の遷移が完了するまで維持する。
- 準備完了通知は、loaderではなく遷移後の描画を経て送る。問題ビューワの未保存編集は、SPA内の移動でも破棄を確認する。

## ゲーム形式

全問題 4 択を基本とする。

メインモニターに Swift のコード、Before / After、API、挙動などを表示し、「これを可能にした Swift Evolution Proposal はどれか？」を参加者が回答する。

例：

```swift
let result = dictionary.compactMapValues { ... }
```

- A. SE-xxxx ...
- B. SE-yyyy ...
- C. SE-zzzz ...
- D. SE-wwww ...

問題文・コードはメインモニターに表示する。スマートフォンには原則として問題全文を表示せず、選択肢と A / B / C / D の大きな回答ボタンを表示する。

回答は 1 問につき 1 回。締切後に正解とランキングを発表する。

### 1 問の進行

| 段階 | Display | Player | Control / サーバー |
| ------------------------------------ | -------------------------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------- |
| 準備 | 待機画面・前問の結果 | 待機・前問の結果 | 進行役だけが次の問題・選択肢・正解を事前確認 |
| 進行役が開始 | 選択肢を伏せた待機画面 | 同左 | その問の参加対象者を確定し、準備を確認 |
| 準備完了待ち | 「全員の接続を待っています」と準備完了人数 / 対象人数 | 同左 | 参加対象者全員の準備完了通知を待つ。Displayは待たない。選択肢は未配信 |
| 選択肢公開前 5 秒 | 残り秒数と横長バー。選択肢は伏せる | 同左 | 全員の準備が揃ってから公開前カウントダウン |
| 選択肢公開・出題まで 20 秒 | 選択肢、出題までの残り秒数と横長バー | 同左。回答不可 | 選択肢の公開から読む時間と出題カウントダウンを一つの20秒として計測 |
| 出題・回答受付（初期値30・45・60秒） | 問題文・コード、選択肢、回答分布、締切までの残り秒数と横長バー | 回答ボタンを有効化し、残り秒数と横長バー | 問題公開と受付開始を一つの状態遷移で実行。ここから回答時間を計測      |
| 回答締切                             | 問題文・選択肢・回答分布を残して締切を表示                     | 回答不可。未回答者は「回答なし」         | 難易度別の設定時間で自動締切。進行役の早期締切も可能                  |
| 正解発表 | 正解・回答分布 | 本人の正誤・順位・時間 | 進行役が公開操作 |
| ランキング発表 | 正解者の先着ランキング | 本人の結果 | 進行役が公開操作 |

進行役が開始すると、準備完了待ち → 公開前5秒 → 選択肢公開・出題まで20秒 → 問題公開・回答受付（難易度1・2・3の初期値は30・45・60秒） → 自動締切と進む。公開前と読む時間は回答時間に含めない。

公開前・選択肢公開中・難易度1・2・3ごとの回答時間は大会ごとの設定値とし、作成時の初期値は5秒・20秒・30秒・45秒・60秒。Control の右ペイン最下部にある「時間の設定」で開始前・進行中に各1〜600秒の整数で変更し、D1へ保存する。設定変更は次に始まる段階から反映し、進行中の段階の期限は変更しない。旧形式の共通回答時間は全難易度へ引き継ぎ、時間設定のない既存大会には新規大会と同じ初期値を使う。数字と横長バーは同じ残り時間を使い、バーの全長はその段階の開始時に確定した時間に、手動延長した時間を加えたものを使う。

回答受付中は、Control の「＋15秒」で現在の回答期限を15秒ずつ延長できる。延長するたびに、3画面のタイマーのラベルを5秒間「15秒延長！」に置き換える。表示領域は増やさず、スマホの選択肢の位置を維持する。延長時刻と期限はD1へ保存し、保存成功後だけ通知・再配信・アラームの再設定を行う。再接続時も同じ期限を使い、5秒以上前のお知らせは再表示しない。次問の時間設定、確定済みの回答、問題公開からの回答時間は変更しない。サーバーで処理する時刻が期限と同じか後なら、締切アラームが未処理でも延長を拒否する。手動締切後も再開できない。

時間と受付状態はサーバーが管理する。各画面のタイマー表示は予告であり、クライアントのタイマーだけで問題公開や回答受付を開始しない。問題文は出題前に Player / Display へ送信しない。

### 3画面の共通進行表示

Player・Display・Control の進行見出し、補足、準備人数、回答人数、残り秒数・バーは共通の表示部品を使う。全段階の文言は `src/client/phase-presentation.ts` に一元化し、画面ごとの違いはレイアウトと文字サイズで表現する。

タイマーの配色と残り5秒以下の色切り替えは `Countdown.tsx` と `Countdown.module.css` に集約する。Control・Display は同じ暗い背景用の配色を使い、Player は明るい背景用の配色を使う。画面別CSSではタイマーの色を上書きしない。数字とバーは同じ色変数を参照する。

読む時間は、全画面で「まもなく出題されます」を見出し、「今のうちに選択肢を読んでおこう」を補足として表示する。残り秒数はタイマーに表示し、見出しには含めない。問題の無効化は「この問題は無効です」とし、参加者個人のお休みと区別する。

Player の回答済み・送信中・回答なし・正誤・順位・途中参加・お休みは、共通案内の下に本人の状態として追加表示する。本人の状態によって大会全体の進行案内を置き換えない。

回答期限に達したら、サーバーの通知待ちでも3画面とも締切表示にする。Display は問題文・選択肢を表示し続け、Player は新しい回答を送らない。Control の正解発表操作は、サーバーが締切状態を確定するまで表示しない。選択肢や問題の公開はクライアントの時計だけでは進めない。

### 参加者の準備完了の確認

- PlayerはWebSocket の受信だけでなく、対象の問題の待機画面を反映し、描画の機会を経てから完了通知を返す。
- 非表示・バックグラウンドの画面は、新たな準備完了通知を返さず、表示状態に戻ってから確認する。
- 出題 ID と配信の世代を通知に含め、別問題や古い接続からの通知を流用しない。
- 同じ参加者の複数タブを複数人として数えない。復帰時は現在の接続で表示を再確認する。
- 準備完了待ちの間に切断した参加者は未準備へ戻す。過去の完了通知だけで全員準備完了とは判定しない。
- Displayは任意の閲覧画面で、複数台をいつでも追加・切断できる。接続台数・準備状態は開始条件に含めず、0台でも参加対象者全員の準備が整えば開始する。
- Displayからは準備完了通知を送らず、表示は運営が目で確認する。Controlには接続台数と各画面の接続状態を表示する。
- 技術的に確認できるのは画面側の表示処理までであり、人が実際に見たことや物理モニターへの投影までは保証しない。
- タイムアウトで勝手に出題しない。未準備の参加者は進行役が「この問題はお休み」にできる。
- Displayの追加・切断・再接続で進行や期限を変更しない。途中で開いた画面には現在の大会状態を配信する。運営が続行困難と判断した場合は問題を無効化できる。

### この問題はお休み

不具合や退室などで参加できない人を、進行役がその問題だけお休みにできる。

- 指定できるのは出題前まで。指定後は準備完了待ちの対象から外し、その問題への回答も受け付けない。
- Player に「この問題はお休みです」と表示する。
- 不正解・未回答とは区別して記録し、その問題の正答率の分母から除外する。
- 次の問題では自動的に参加対象へ戻す。退室したままなら、再びお休みにできる。
- 出題後に未回答者をお休みに変えて、正答率を後から変える操作は設けない。
- 準備完了待ち中にお休みを指定し、残りの参加者全員の準備が整ったら、選択肢公開前のカウントダウンを開始する。
- 参加対象者が 0 人なら出題せず、Control にその旨を表示する。

Displayの表示確認は運営が目で行い、システムによる待ち合わせはしない。問題を続行できなければ無効化してスキップする。

## 問題の方向性

大部分は単純な Proposal title 暗記ではなく、次のような材料から Proposal を判断する問題にする。

- コード
- Before / After
- API
- 言語仕様の変化
- コンパイル可能になったコード

ただし、すべてを熟考問題にはしない。`compactMapValues` の導入のような「知っていれば見た瞬間押せる」早押しクソ問題も意図的に少数混ぜる。

これは元祖 Swift Evolution カルタの高速早押し感を残すための要素。問題によって回答時間が 0.x 秒〜十数秒まで大きく変わって構わない。

初期版では誤答への減点を設けない。4 択を推測して早押しする戦略にも利益があることは許容し、早押しの賞には運の要素も含まれるものとする。

## 画面

大会中の画面は Display / Control / Player の3種類に分ける。このほかに、大会一覧・作成画面と、準備用の問題ビューワ・Displayプレビューがある。

### Display

会場の複数モニターや参加者のPCを使ったサテライト表示用。同じ大会のDisplay URLを開き、Display用パスワードで認証すれば、各画面に同じ進行・問題・期限を配信する。通常の 16:9 モニター / プロジェクターに収まるレイアウトにする。

カウントダウン開始後に追加した画面は現在の状態に合流し、追加・切断を理由に進行を巻き戻さない。参加者は回答用のPlayer画面とサテライト用のDisplay画面を別ウィンドウ・端末で使える。

認証・初期接続を終えた進行中の画面には管理操作を置かず、Control の UI やマウス操作を見せない。

表示内容：

- 大会名、参加用 QR コードと参加コード、問題番号
- 選択肢、準備完了待ち、読む時間、出題カウントダウン
- 出題後の問題本文、Swift コード等
- 回答受付状態
- 正解と回答分布、問題ごとの先着ランキング、最終結果
- 接続が切れた場合の再接続中表示

URL を知った人が不用意に開くのを防ぐ程度の表示パスワードを設ける。閲覧権限だけを与え、管理操作は許可しない。

解説は進行役が口頭・アドリブで行うため、Display には解説文を表示しない。問題 JSON の `explanationMarkdown` は保持し、Control・問題ビューワ・試合後レポートでは引き続き確認できる。

### Control

進行役が PC で操作する管理画面。管理用パスワードで認証する。

表示・操作：

- 次の問題・選択肢・正解・解説の事前確認
- 接続・準備確認から始める「開始」操作
- Display の接続台数・接続状態（表示は運営が目で確認）
- 参加者ごとの接続・準備完了・お休み状態
- 「準備完了 28 / 30 人」のような人数と、未準備の参加者一覧
- 出題前の「この問題はお休み」操作
- 読む時間・カウントダウンの進行状況
- 回答済み人数 / その問の回答対象人数
- 回答受付中の15秒延長、回答締切、正解表示、ランキング表示、次の問題、大会終了
- 問題の無効化・スキップ

接続人数、参加対象人数、準備完了人数、回答人数を混同しない。接続状況は参考情報であり、切断だけで参加対象者を自動的に除外しない。

現在できる操作だけを有効にし、通信中の二重クリックで状態が二段階進むことを防ぐ。

### Player

スマートフォン利用を第一に設計する。

参加時は大会名、名前入力、参加ボタンを表示する。ログイン・アカウント作成は不要。

選択肢公開後は A / B / C / D と各選択肢の文言を表示し、大きなボタンで回答できるようにする。問題文は原則として表示しない。

準備待ちと公開前カウントダウンでは選択肢を表示しない。選択肢公開後も受付開始前は回答ボタンを無効にし、出題までの残り秒数と横長バーを表示する。次問では前問の選択状態・送信待ち・ボタンのフォーカスを持ち越さない。

回答の状態は `未回答 → 送信中 → 回答済み` とする。ボタンを押しただけでは回答済みにせず、サーバーの保存完了を待つ。受理された選択肢も表示する。

正解発表後は、本人の正誤、正解者内順位、回答時間を表示する。例：

```text
✅ 正解
正解者 18 人中 6 位
1.830 sec
```

不正解・未回答・お休みは区別する。不正解者に正解者内順位を表示しない。

## 最小アーキテクチャ

| 構成要素 | 責務 |
| ------------------ | ------------------------------------------------------------------------------------------- |
| Cloudflare Workers | 静的画面の配信、認証、API、接続を大会の Durable Object に振り分ける |
| Durable Objects | 大会ごとに 1 個。WebSocket 接続、準備完了の待ち合わせ、進行、タイマー、回答受付、通知を担当 |
| D1 | 問題、大会、進行状態、出題、参加者、参加資格、回答の永続化 |

保存データの正本は D1 に統一する。Durable Object のメモリは接続管理と復元可能な状態に使い、独立した大会データの正本を二重に持たせない。

Durable Object の再起動後は D1 から復元する。準備完了待ちなら現在の接続で表示を再確認し、時間進行中なら保存した期限と状態から復旧する。過去のタイマーが別の問題を開始しないよう、出題 ID・状態・更新番号を確認する。

大会進行中の状態変更と回答は、その大会の Durable Object を経由する。D1 に対する非同期処理中も回答・締切・タイマーが競合し得るため、処理順と DB 制約を明示的に設計する。D1 の永続化完了後に成功通知・確定した状態を配信する。

初期版では進行データにキャッシュや読み取りレプリカを導入せず、D1 のプライマリを使う。

フロントは TypeScript + React + Vite、Worker / Durable Object も TypeScript で実装する。フロントと API は同一オリジンにまとめる。問題の確認・調整には準備用の問題ビューワを使い、編集結果は JSON として保存して新しい大会に取り込む。問題マスターや既存大会へ直接書き戻す管理 UI は設けていない。

### リアルタイム同期と復帰

- Display / Control / Player は WebSocket で現在の大会状態を購読する。
- 接続・再接続時に、権限に応じた現在状態と本人の回答を取得する。
- 各通知に出題 ID と状態の更新番号を含め、古い通知で表示を巻き戻さない。
- 切断時は接続状態を表示して自動再接続する。回答の受付状況が不明なまま「回答済み」にしない。
- 同じブラウザーでは再読み込みしても参加者セッションを復元する。通常の進行でリロードは不要。
- 再接続は新規参加として扱わない。出題中の再接続でも、対象者なら締切まで回答できる。
- 通知を逃しても現在状態から復帰できる設計にし、過去の全通知の再送は必須としない。

## データモデル

以下はデータの責務と制約。実際の型は `src/shared/types.ts`、SQL スキーマは `migrations/0001_initial.sql`、保存・復元処理は `src/worker/repository.ts` に定義する。

### Question

大会から独立した再利用可能な問題原本。

- `id`
- `difficulty`：1（入門）・2（標準）・3（難問）。旧JSON・保存済み大会で省略されている場合は2として読み込む。nullや範囲外・非整数は受け付けない。
- `bodyMarkdown`：問題文と Swift コードブロック。複数のコードブロックで Before / After も表現可能
- `choices`：A / B / C / D の 4 件。Proposal 番号とタイトルを含む
- `correctChoice`：A / B / C / D のいずれか 1 件
- `explanationMarkdown`

難易度は表示と回答受付時間の選択に使い、得点・最多得票との比較による難問王の計算には使わない。Displayには問題開始後の接続待ち・選択肢公開前のカウントダウンから数字と3段階の星を表示し、選択肢公開中も問題の予告として見せる。問題本文の公開後は本文の前に表示する。参加者端末には難易度を送らない。Controlの事前確認・問題ビューワにも同じ部品で表示し、ビューワで編集・JSON保存できる。本文の自動サイズ調整ではバッジの領域も含めて計測する。

Markdown の任意 HTML は許可しない。問題データは事前にレビュー済みの JSON から取り込み、選択肢数・正解の妥当性・必須項目を検証する。不正なデータは登録時にエラーにする。

コードブロックの言語名（`swift` など）に応じて、共通の Markdown 表示部品で同期的にシンタックスカラーリングする。Control・問題ビューワの問題文と解説、Display の問題文に適用し、暗い背景では共通の暗色用配色を使う。言語未指定・未対応言語・プレーンテキストはそのまま表示する。

### Tournament

- `id`, `name`, `createdAt`
- `phase`：大会の進行状態
- `currentIndex`：現在の出題の配列位置。開始前は -1
- `revision`：状態の更新番号
- 表示パスワードの検証用情報
- `timing`：`countdownSeconds`（初期値5）、`readingSeconds`（初期値20）、`answeringSeconds1`（難易度1、初期値30）、`answeringSeconds2`（難易度2、初期値45）、`answeringSeconds3`（難易度3、初期値60）
- `phaseEndsAt`：進行中の段階の期限。時間設定を変更しても維持し、回答受付中の手動延長でのみ15秒を加算する

実装上の大会全体の型は `Game`。進行状態は `tournaments.state_json` に保存し、参加者と出題は別テーブルから復元する。大会作成時に問題と順序を確定し、作成済み大会の問題内容・順序・採点条件を編集する機能は設けていない。

### TournamentQuestion

大会内の個別の出題。実装では `Round` 型と `rounds` テーブルに対応する。単なる問題原本への参照ではなく、その大会で使った内容を保持する。

- `id`, `tournamentId`, `questionId`, `order`
- 問題本文・選択肢・正解・解説のスナップショット
- `readingStartedAt`, `countdownStartedAt`, `openedAt`, `closedAt`
- `answerExtendedAt`：最後に回答時間を延長した時刻。延長していない出題や旧大会では省略
- `isVoided`, `voidReason`

問題原本を修正しても、作成済み大会の内容や過去の結果は変わらない。時刻はサーバー基準のミリ秒で保存する。

### Player

- `id`, `tournamentId`, `name`, `joinedAt`
- ランダムな本人識別セッションの検証用情報

名前は表示用であり本人識別には使わない。同名は許可し、Control では短い識別子も併記する。前後の空白を取り除いた名前を1〜20文字に制限し、空白のみの名前は拒否する。

大会途中の新規参加は許可するが、進行中の問題には加えず次の問題から対象にする。

### QuestionParticipation

その問題に誰が参加対象だったかを保存する。

- `tournamentQuestionId`, `playerId`
- `status`：`eligible` / `resting`

準備確認の開始時に対象者の一覧を作る。途中参加者にはその問の行を作らず、以前のお休み状態を次の問題へ引き継がない。

準備完了状態は接続に依存するため、保存された過去の完了情報だけで待ち合わせを通過させない。

### Answer

- `tournamentQuestionId`, `playerId`
- `choice`
- `receivedAt`：大会の Durable Object が回答を受信した時刻

回答は `Question.id` ではなく大会内の出題 ID に紐づける。`(tournamentQuestionId, playerId)` に一意制約を設け、同じ出題への回答を上書きしない。

回答者・出題が同じ大会に属すること、参加資格があることも検証する。

## 状態遷移

通常の流れ：

```text
waiting
  → choicesPreparing       選択肢を伏せて準備完了待ち
  → countdown              全員が準備完了。選択肢公開まで 5 秒
  → choicesReading         選択肢公開。出題まで 20 秒
  → acceptingAnswers       問題公開・回答受付開始
  → answersClosed          難易度別の設定時間で自動締切（早期の手動締切も可能）
  → answerRevealed          回答分布を維持して正解を強調
  → rankingShown           正解者の先着ランキングを公開
  → choicesPreparing       次の問題を開始
  または finished          大会終了
```

Control だけが手動の進行操作を行える。`choicesPreparing → countdown → choicesReading → acceptingAnswers → answersClosed` は条件成立・時間経過によるサーバーの自動遷移とする。

次の問題の事前プレビューは Control 内だけの表示であり、公開状態を変えない。

状態変更は対象の出題 ID・期待する更新番号を検証する。二重クリック、古い Control、古いタイマーによる操作を再適用しない。許可されていない遷移は拒否して最新状態を返す。

### 無効化・スキップ

問題ミス、誤操作、通信障害への対処として、進行役は現在の問題を無効化できる。

- `questionVoided` 状態に移り、受付と当該問題のタイマーを停止する。
- 既存の回答は削除せず、無効理由とともに残す。
- その問題をすべての表彰、回答時間記録、正答率、安定王の対象問題数から除外する。
- 無効化後は次の問題へ進むか大会を終了する。
- 同じ出題の巻き戻し・再受付は初期版では行わない。

最終結果は終了時点で集計する。途中で大会を終了する場合、未完了の問題は無効化してから終了し、未出題の問題も集計対象にしない。

## 回答受付と回答時間

回答時間は `receivedAt - openedAt` とする。読む時間・カウントダウン・D1 保存完了までの処理時間は含めない。

`openedAt` はサーバーが実際に受付開始へ遷移する時刻とする。タイマーの遅延や再起動で出題が遅れても、過去の出題予定時刻へ遡って計測を開始しない。

`receivedAt` はサーバー内の処理待ちや保存を始める前に取得する。参加者端末の申告時刻で順位を決めない。

自動締切の期限ちょうど以降に届いた初回回答は、アラーム処理が遅れていても拒否する。期限までに有効な回答を受信しなかった参加者は回答なしとし、回答レコードを作らない。

回答と締切は大会単位で処理順を定め、受付中に受信した有効な回答を保存してから締切を確定する。締切後の初回回答、出題前の回答、お休み・対象外の参加者の回答、別の問題への回答を拒否する。

通信切断などで応答が失われた場合は同じ回答を再送できる。既に保存されていれば、締切後でも元の回答と時刻を返す。別の選択肢を再送しても上書きしない。未保存の回答を締切後の再送で遡って受理しない。

実際の問題表示や回答送信の通信時間は計測値に影響する。この値はシステム上の回答所要時間であり、純粋な反応時間ではない。厳密な端末間時刻同期や遅延補正は導入しない。

同じ記録時刻の正解者は同順位とし、順位は `1, 1, 3` の形式にする。表示の丸めで同じ秒数になっただけの場合は、保存したミリ秒で順位を計算する。

## 問題ごとの結果

正解公開前には正誤・正解者順位・解説を Player / Display に送らない。

正解発表後、Player は本人の結果を表示する。その後のランキング公開操作で、Display に正解者の先着ランキングを表示する。

Displayには回答受付開始から順位公開まで、A〜D順の横棒グラフで回答人数を表示する。回答前から他の人の票を見て選ぶ遊び方を認め、サーバーで保存した回答が増えるたびに、タイムバーと同じ幅の100msの線形補間でバーを伸ばす。100%は当該問題の回答対象人数で固定し、お休み・途中参加でその問題の対象外だった人は含めない。回答済み人数 / 対象人数と未回答人数を併記し、0人の選択肢も残す。回答中は全選択肢を同じ色で表示し、締切後も集計を維持する。正解発表では同じ位置・長さのバーを残して、正解の行だけ色と「正解」の文字で強調する。

回答分布はサーバーで集計し、回答受付中・締切後・正解発表・順位公開時のDisplayにだけ人数を送る。Player・Controlへの集計の追加配信は行わず、正解・解説は従来どおり正解発表まで公開しない。途中接続・再接続でも現在の集計を復元し、次問・無効化・大会終了で消す。参加者名や個別回答は追加配信しない。終了後の管理画面と人数の集計処理を共用する。

```text
1. Alice — 0.820 sec
2. Bob   — 1.140 sec
3. Carol — 1.390 sec
```

Display は正解者の先着ランキングを先頭8人まで、Control は全件表示する。Player では表示件数に関係なく本人の順位を確認できる。表示件数と会場画面での収まりは本番前に確認する。

## 最終リザルト

複数観点で表彰し、最速の 1 人以外も楽しめるようにする。4種類の表彰と大会最速回答は実装済みで、大会終了時に3画面へ表示する。Display は各表彰の先頭3人まで、Control / Player は全件表示する。

以下が現在の集計ルール。同点は同順位とし、無理に単独の優勝者を作らない。表彰条件を変更するUIはなく、ルールを見直す場合は本番の大会作成前に実装と表示を揃える。

### 正答王

有効な問題の正答数ランキング。未回答・お休み・途中参加前の問題では正答数を加算しない。

### 早押し王

各問題で正解者内 1 位を取った回数。同着 1 位は全員に 1 回を加算する。

### 安定王

正解した問題の正解者内順位の平均が小さい人を表彰する。

初期条件は「大会全体の有効問題数の半数以上に正解した人」を対象とする。必要正答数は切り上げ、最低 1 問とする。お休みや途中参加で個人ごとの必要正答数を下げない。

1 問だけ正解して 1 位だった人が有利になりすぎないための条件。この条件で実装済みであり、本番用の問題セットと試遊結果で表彰の妥当性を確認する。

### 難問王

締切時の最終集計で、正解の選択肢が最多得票ではなかった問題を難問とし、その正答数で表彰する。条件は `正解の票数 < A〜Dの最多得票数`。同率最多に正解が含まれる場合は対象外とする。

票数はその問題の eligible な参加者の回答だけで数え、未回答・お休み・対象外の人は票を持たない。全員未回答の場合は対象外。正解0票で他の選択肢に票がある場合は対象問題に数えるが、加点される人はいない。無効問題・未完了問題は含めない。旧 `difficultyThreshold` は参照せず、保存済み大会の最終結果・終了後レポートもこの条件で再集計する。

作問時に指定する `difficulty` は表示用であり、難問王の判定には使わない。対象問題数も表示し、対象問題がない場合は0問・「該当者なし」と表示する。

### 集計共通

有効問題がない場合や表彰条件を満たす人がいない場合は「該当者なし」と表示する。正答王・早押し王・難問王で実績が 0 の人を受賞者として扱わない。

## 大会記録

4 ランキングとは別枠で「大会最速回答」も表示する。

対象は有効な問題への正解のみ。誤答・無効問題は対象外。同じ最速記録があれば併記する。

```text
Fastest Answer
0.382 sec — Dave
compactMapValues(_:)
```

瞬殺問題で異常な速度が出ること自体を笑える要素にする。

## 大会の詳細結果（管理者専用）

終了した大会のControlに「詳細結果を見る」を表示し、`/e/:id/control/report` へ遷移する。管理用パスワードで認証する。大会進行用のWebSocketは使わず、ページのloaderで保存済みデータを取得してから表示する。

| 画面 | 確認できる内容 |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 全体の集計 | 有効・無効・未出題の問題数、全体正答率、回答数と延べ参加対象数、全回答の平均時間、4種類の表彰・大会最速回答 |
| 問題ごとの内訳 | 出題順・正答率順の一覧、問題本文・選択肢・解説、参加状況、正答率、A〜Dの回答人数、全回答の平均・中央時間、最速正解時間、全参加者の回答・正誤・時間・正解者内順位 |
| 参加者ごとの成績 | 名前・識別子での検索、正解数・正答率・正解時の平均時間・名前での並べ替え、正解・不正解・未回答・お休み・対象外の件数、全回答と正解のみの平均時間、最速正解時間、1位回数・平均順位・安定王の資格・難問正解数、全問の回答履歴 |

問題の回答一覧から参加者の詳細へ、参加者の履歴から問題の詳細へ移動できる。同名参加者は短い識別子で区別する。

集計ルール：

- 有効問題の判定、正解者内順位、難問の判定、最終表彰は既存のゲーム集計を共用する。
- 全体・個人成績から無効問題と未出題を除外する。全体正答率は有効問題の正解数の合計 ÷ 延べ参加対象数であり、問題別正答率の単純平均ではない。
- 正答率の分母に未回答を含め、お休み・途中参加前などの対象外を除く。分母が0なら「—」を表示する。
- 平均・中央値は回答済みデータのみを対象とし、未回答を0秒として扱わない。「全回答」と「正解のみ」の時間を区別する。
- 無効問題の詳細には理由と保存済み回答を残し、集計対象外であることを明示する。順位は付けない。受付開始前に無効になった参加対象者は「受付前」とし、未回答に数えない。
- 未出題の問題は全員の履歴を「未出題」とする。問題別の棒グラフは参加対象数を分母とし、未回答分をA〜Dへ割り振らない。

取得APIは `GET /api/e/:id/report`。管理者以外には401、未終了の大会には409を返す。終了後のD1を読み取り、問題は大会作成時のスナップショットを使う。レスポンスは `Cache-Control: no-store` とし、参加者セッションの検証情報や表示パスワードのハッシュを返さない。既存のPlayer / Display向け配信には詳細結果を追加しない。

結果のJSONダウンロードは採用せず、CSVダウンロードも今回の実装には含めない。画面表示に必要なAPIのJSON応答と、ファイルとしての結果出力は別扱いとする。

ローカル確認には `npm run seed:report` を使う。16人・12問（有効8・無効2・未出題2）の終了済み大会を、新規の大会・問題IDでローカルD1に追加する。既存大会と問題原本は変更せず、本番DBには接続しない。

## URL と認証

- `/e/:id/display`：大会ごとの表示用パスワードで閲覧
- `/e/:id/control`：管理用パスワードで認証
- `/e/:id/control/report`：同じ管理用パスワードで終了済み大会の詳細結果を閲覧
- `/e/:id/play`：名前を入力して参加。以後は参加者セッションで識別

初期版の管理用パスワードは運営用の共通シークレットとし、ユーザーアカウント管理は作らない。表示用と管理用の権限を分離する。

認証後は Cookie セッションを使い、パスワードを URL に入れたり、平文で DB に保存したりしない。WebSocket 接続・メッセージにも認証と権限確認を適用する。Cookie の保護と Origin の確認も行う。

本人識別セッションはランダムに生成し、名前や公開の参加者 ID だけで回答できないようにする。同じブラウザーのセッション復帰は実装済み。別端末への本人引き継ぎは、短期間のイベント向けには不要なため実装対象外とする。

問題 JSON・正解・解説を公開の静的ファイルやフロントのバンドルに含めない。役割と公開段階に応じてサーバー側で送信内容を制限する。

参加者には `/e/:id/play` の QR コードに加え、英字6文字の参加コードとトップページURLを表示する。Controlでは進行中も、Displayでは待機中に表示する。

- トップページ `/` の参加フォーム → コードの確認 → 既存の参加画面で名前を登録、の順で入る。管理者ログインは不要。
- I・L・O を除いた大文字英字をランダム生成し、画面では3文字ずつ区切る。入力は小文字・空白・全角を正規化する。
- 大会作成時に発行し、D1の `tournaments.join_code` に保存する。一意制約で衝突を検出して再発行し、通常の状態更新や再起動では変更しない。`state_json` には重複保存しない。
- `0002_join_code.sql` を適用後、既存大会は初回参照時にコードを発行する。同時参照でも保存済みのコードへ収束し、既存結果は保持する。
- `GET /api/join-code?code=...` は大会名・ID・参加URLのみを返す。形式不正は400、存在しなければ404、終了済みなら410。すべて `Cache-Control: no-store`。
- 終了済み大会は新規参加不可。既存の参加者セッションでの結果閲覧は維持する。コードは公開識別子であり、Control / Display の認証を代替しない。

## 当日の UX と非目標

参加者はシステムの使い方を学びに来ているわけではない。説明なしに使えるレベルを目指す。

- ログイン・アカウント・複雑なプロフィールは不要。
- 問題形式は 4 択に統一し、回答は A / B / C / D を押すだけ。
- スマートフォンばかりを見るのではなく、前方のモニターを見る体験を維持する。
- 切断・送信中・回答済み・お休みを明確に区別する。

初期版では次を行わない。

- 当日の AI 問題生成・LLM 連携
- 高度なユーザーアカウントシステム・SNS 機能
- 大量の問題形式・過剰なアニメーション
- 本格的な不正対策・ミリ秒単位の厳密な分散時刻同期
- 汎用クイズ SaaS 化・複数会場の同時運営に特化した UI
- 問題マスターや既存大会への直接編集・同じ出題の巻き戻し（準備用の問題ビューワは実装済み）

「実際のイベントで確実に動くこと」を優先する。

## 実装済みの範囲と検証

最初のマイルストーンだった「1 問を最初から最後まで遊べる縦切り」は実装済み。現在は次の範囲をローカルで試遊できる。

1. 検証済みの問題 JSON から Tournament を作れる。
2. 認証・権限を分けた Display / Control / Player が開ける。
3. 名前を入力して参加し、再接続・再読み込みでも本人として復帰できる。
4. 進行役が事前確認し、選択肢を公開できる。
5. 準備完了を待ち合わせ、未準備の人をその問だけお休みにできる。
6. 全員の準備完了後、公開前5秒、選択肢公開・出題まで20秒、問題公開・回答受付（難易度1・2・3の初期値は30・45・60秒）、自動締切と進む。公開前・選択肢公開中と難易度別の回答時間は大会ごとに変更でき、次の段階から反映する。
7. 1 回だけ回答でき、再送・切断・締切との競合を処理できる。
8. 締切、正解、先着ランキングをリロードなしで表示できる。
9. 問題の無効化・スキップと、次の問題への遷移ができる。
10. 大会終了時に4種類の表彰と大会最速回答を表示する。
11. 問題ビューワで確認・編集し、JSONとして保存できる。本番と同じDisplayレイアウトを別タブで確認できる。
12. 難易度の数字・星、Swiftコードのシンタックスカラーリング、Displayの本文自動サイズ調整を表示できる。
13. 管理者専用の詳細結果画面で終了済み大会の集計・回答履歴を確認できる。ローカルDBへ終了済みダミー大会を追加できる。

## ローカル初期実装・公開URL

- 開発ポートは `5218`（SE-0218 に由来）。他プロジェクトとの衝突を避け、使用中の場合は自動で別ポートへ移らない。
- サーバーの公開元URLを必須設定 `PUBLIC_ORIGIN` とする。例：ローカル `http://192.168.1.2:5218`、本番 `https://公開ホスト名`。スキーム・ホスト・必要なポートだけを指定する。
- QR・参加URL・各画面への絶対URLはサーバーがこの設定から生成し、`Host` / `X-Forwarded-Host` に依存しない。別名で開いたクライアントは公開URLに移動し、WebSocket と Origin 検証も同じ設定を使う。
- 公開ホスト変更でブラウザーセッションが別扱いになるため、大会開始前に確定する。
- 配色は Swift 公式ロゴのオレンジ `#F05138` を基準とする。Display は暗い背景、スマートフォンと Control は明るい背景とし、文字のコントラストに合わせて濃淡を調整する。
- 初期実装はローカルの Workers / Durable Objects / D1 で動作確認する。本番の Cloudflare 環境は作成・変更しない。

## 問題ビューワ（準備用）

`/questions` に管理用パスワードで開く問題ビューワを実装済み。大会一覧・Control から移動できる。

- 大会に固定された問題集を出題順に読み込む。または手元の JSON ファイル・貼り付けた JSON を読み込む。
- 問題一覧・検索・前後移動で確認する。本番画面と共通の Markdown / 選択肢表示を使い、正解・解説の表示と暗い背景を切り替えられる。
- 正解の A〜D の分布を表示する。
- 問題ID・問題文・選択肢・正解・解説をブラウザー内で調整し、プレビューへ反映する。
- 問題集は共通バリデーターで検証する。不正なファイルは全体を拒否し、編集による不正がある間はダウンロードを無効にする。
- 編集結果は JSON としてダウンロードし、新しい大会の作成時に取り込む。元ファイル・問題マスター・既存大会には書き戻さない。
- 配列形式と `{ "questions": [...] }` 形式の両方を扱う。後者の大会名などの付随情報は出力時に保持する。
- 編集内容は画面内に保持し、未ダウンロードの変更がある場合は問題集の切り替え・ページ離脱時に確認する。自動保存は行わない。
- 大会の問題取得APIは管理者限定とし、参加者・Display に未公開問題や正解を返さない。
- 「Displayプレビューを開く」は別タブへ開く通常のリンクとし、別ウィンドウへの移動はブラウザーの操作に任せる。本番Displayと同じ `DisplayScreen`・進行表示・CSSを使い、文字サイズ・余白・スクロール条件を一致させる。
- プレビューは初期状態を出題中とし、選択肢公開・正解発表にも切り替えられる。出題中と正解発表では「サンプル」と明記した同じ20人分（回答18・未回答2）の回答分布も表示する。タイマーは選択肢公開20秒・出題中は難易度1・2・3に応じて30・45・60秒の初期値で固定する。選択問題・未保存の編集・問題集の切り替えを自動反映する。
- プレビューはビューワごとに識別した通信先との同一オリジンの BroadcastChannel 通信だけで問題を受け取り、大会への接続・問題取得・登録・ブラウザーへの永続保存を行わない。再読み込み時は最新状態を受け取り直す。ビューワから離れると案内表示に戻る。
- 出題中・締切後の正解発表待ち・正解発表では `100dvh` 内にコンパクトなヘッダー・進行案内・2列×2段の選択肢を配置する。画面の縦横比による高さ制限の有無を作らず、本文には残りの高さを割り当てる。出題中から正解発表までは本文の横に回答分布を配置し、狭い画面では本文の下に配置する。Display プレビューでも解説文は表示しない。
- 本文は `FittedQuestion` で実際のMarkdown DOMを計測し、縦横とも収まる最大の文字サイズを1〜32pxの範囲・0.25px単位で選ぶ。コードは折り返さず、行間1.35とする。問題文・コード・注記を一緒に調整し、計測用の別レイアウトやtransformによる縮小は使わない。
- 初回・本文変更・表示段階変更は `useLayoutEffect`、表示領域の変化は `ResizeObserver` で描画前に同期計測する。探索途中を描画フレームに分けず、未計測の本文は非表示にする。外枠の高さは本文から独立させ、計測ループを防ぐ。画像・フォントの読み込みによる組版変化も再計測する。タイマーや回答人数だけの更新では再計測しない。
- プレビューからビューワへ表示領域・文字サイズ・収まりを返す。18px未満なら短縮を案内し、最小サイズでも収まらない場合は不適合を表示する。後者は内容を黙って切らず、スクロールで確認できるようにする。18pxは会場での可読性を保証する値ではなく、問題作成時の確認目安とする。
